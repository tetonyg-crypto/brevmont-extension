# AGENTS.md — brevmont-extension

The Brevmont Chrome extension (MV3, WXT, React 19, TypeScript). Read this
before touching code so the loops the founder lived through (version
chaos, stale Desktop folders, "which build is actually running") don't
get re-introduced.

## What this extension is
- Chrome side-panel workflow for Gmail, Messenger, LinkedIn, VinSolutions
- Posts events to `https://api.brevmont.com/api/v1/events` (canonical) and
  `/api/v1/log-action` (legacy v1.10 path, sunset June 2026)
- MV3 service-worker background, WXT 0.20, React 19 panel UI
- Cookie-share auth via `brevmont_rep_session` from `app.brevmont.com`

## Hot files
- `entrypoints/background.ts` — service worker entry, install/update
  handshake (`onInstalled` → `/api/v1/extension-loaded` + `/v1/health/extension-ping`)
- `entrypoints/lib/honestEvents.ts` — `logEvent`. Stamps `ext_version`
  into every payload. Don't bypass this — anything that POSTs to events
  goes through `logEvent`.
- `entrypoints/content/` — DOM observers per host
- `scripts/ship.mjs` — one-command build + Desktop sync + zip + API
  copy. NEVER cobble this together by hand again.
- `manifest.json` (generated by WXT from `wxt.config.ts`) — version,
  permissions, host_permissions

## Required patterns

### Single ship path
**One Desktop folder on this Mac:** `/Users/yancygarcia/Desktop/Brevmont-<version>-UNPACKED`.
Every extension release, auth fix, build handoff, or "try this version"
MUST run `npm run ship` so stale Desktop builds/zips are deleted and
the current versioned folder is re-filled with the newest build. Do not
say an extension change is done until the versioned Desktop folder's
`manifest.json` shows the new version. Do NOT load an older versioned
folder in `chrome://extensions`.
Do NOT keep `brevmont-extension-v1.13`, `brevmont-extension-old`,
`brevmont-extension-backup`, old `Brevmont-<version>-UNPACKED` folders,
old `brevmont-extension-<version>-chrome-web-store.zip` files, or the
lowercase `brevmont-extension` folder on Desktop — they confuse which
version is actually running. See Lab Note 2026-04-29.

### Version stamping
Every event posted by the extension MUST include `ext_version` in
`action_metadata`. `honestEvents.ts:logEvent` does this automatically by
calling `chrome.runtime.getManifest().version`. New event paths must go
through `logEvent`, not raw `fetch`.

### Install/update handshake
`background.ts onInstalled` MUST fire two calls in parallel:
1. `POST /api/v1/extension-loaded` — Telegrams the founder ("🔌 v1.14.1 update")
2. `POST /api/v1/health/extension-ping` — quiet heartbeat, returns
   `{ db, latest_known_version, stale }`. Stale flag goes into
   `chrome.storage.local.brevmont_ext_version_stale` for the panel UI.

Don't remove either. The Telegram one is how the founder confirms a load
worked; the heartbeat is how the API logs version distribution.

### Auth
- `rep_auth_token` lives in `chrome.storage.local`
- Reps activate via cookie-share from `app.brevmont.com` (no manual key
  entry; the legacy 4-step setup wizard is gone as of v1.10.0)
- Required manifest permissions: `cookies`, `*://*.brevmont.com/*`

## Hard "Do Not" List
- DO NOT remove the `npm run ship` script or replace it with manual steps
- DO NOT load any extension folder other than the current versioned
  Desktop path
- DO NOT finish or report an extension fix until the current versioned
  Desktop folder has been refreshed and manifest-verified
- DO NOT add new fetch calls bypassing `honestEvents.logEvent` for events
- DO NOT bump version in manifest.json directly — bump `package.json`
  and let WXT wire it through (per `scripts/ship.mjs` flow)
- DO NOT skip `npm run build:release` in CI — it runs registry sync
  verification and catches drift between the host allowlist and the
  content scripts that exist
- DO NOT ship without reloading via `chrome://extensions` and watching
  Telegram for the load confirmation

## Testing commands
- Build: `npm run build`
- Build for release (with verifiers): `npm run build:release`
- Ship to Desktop + API: `npm run ship`
- Playwright tests: `npm test`
- Mock-DOM tests: `npm run test:mock-dom`

## Self-Service Commands
- Current version: `node -p "require('./package.json').version"`
- Live API version: `curl -s https://api.brevmont.com/health`
- DB-version distribution: PostgREST query on `event_log_v2.action_metadata->>'ext_version'`

## When a load doesn't take
1. Check `chrome://extensions` shows the right version pinned
2. Check Telegram fired the load confirmation — if not, the service
   worker errored out before `onInstalled`. Look at the extension's
   service-worker DevTools console.
3. Check `chrome.storage.local.brevmont_ext_version_stale` — if true,
   the API knows about a newer version and the user is behind.
4. If Gmail still shows the old behavior, hard-refresh the Gmail tab
   (content scripts only re-inject on navigation).
